# 桌面控制验收

本页维护可重复执行的验收方法。能力探测、模块测试、真实 Runtime 工具调用、完成桌面任务及安装包验收分别记录；历史通过结果只适用于当时的源码、二进制和平台。

## 环境与准备

当前固定驱动运行于 macOS，需要可访问且已解锁的图形会话，以及实际验收应用的辅助功能和屏幕录制权限。终端或单元测试程序获授权不代表应用具有同样授权；重新签名后应重新核对。

先按 [开发与验收](../testing.md) 准备显式私有模型资源、检索模型、Theia、Office 和前端，再构建带 `tauri/custom-protocol` 的程序。该驱动创建独立的私有数据目录和合成工作区，不复用真实会话或业务资料。

```sh
node scripts/validate-native-desktop-controls.mjs src-tauri/target/debug/echoagent --task-flow
```

驱动记录源码构建产物、实际签名副本、固定夹具、应用 PID 和模型身份。需要系统目录选择器时，核对自有 PID、完整路径及持久授权。普通开发服务器地址不能作为独立内嵌应用验收。

## 模式与完成条件

| 运行方式 | 范围与判定 |
| --- | --- |
| 不带模式参数 | 只读 Runtime 接入资格：真实工具身份、分页和暂停；`desktopAcceptance` 不标为完成 |
| `--smoke` | 短文稿输入、读回、保存和暂停；有活动执行预算，不替代完整跨应用验证 |
| `--journey` | 合成桌面场景准备及操作记录；各场景须分别核验实际结果 |
| `--task-flow` | 明确新建空文稿、精确正文、现有消息停止按钮、停止静默、同任务普通消息继续及真实保存；完成后必须运行独立核验器 |
| `--universal-flow` | 在严格任务流程上追加 Safari 的本地合成页面输入与系统文件选择；不代表任意应用已通过 |
| `--opaque-flow` | 真实模型和正常 Composer，缺正文时等待，单独继续仍等待，再补正文；操作没有 AX 输入焦点的临时自绘 App，真实点击、输入和发送到夹具文件，宿主精确核验并提交完成凭证，驱动独立检查文件和 Runtime journal |
| `--wechat-flow` | 显式真实发送：须已获用户授权，并设置 `ECHO_DESKTOP_REVIEW_WECHAT_SEND=1`。正常 Composer 和真实模型操作本机微信，只向文件传输助手发送固定测试正文一次；宿主 OCR 分别核验微信窗口的会话标题和消息记录区域，核验凭证必须晚于发送。驱动读取原始 journal，不能以模型总结替代证据；结果未知时不得直接重跑发送 |

任务模式通过正常 Composer 提交用户请求并点击其已有停止按钮，由实际模型与生产 Native MCP 操作桌面。驱动只准备合成输入与记录证据；不能通过 Shell、直接文件写入、CDP 或测试 IPC 代做目标文稿。

驱动打印的 `home` 为本次验收目录。待流程完成后，将下面的目录替换为该实际值：

```sh
ACCEPTANCE_HOME='/path/to/acceptance-home'
node scripts/verify-native-desktop-task-flow.mjs "$ACCEPTANCE_HOME"
```

独立核验要求原始 Runtime journal、当前会话和模型身份相符，并联合检查：

- 本轮实际执行新建命令，在空文稿中输入本轮独有正文。
- 实际读回与用户全文逐字一致，保留中文、特殊字符及明确要求的末尾换行。工具的 `verified` 仅证明该次入参被满足，不能替代用户要求。
- 现有消息停止按钮撤销执行权，取消确认后的静默区间没有实体操作；普通消息“继续保存”在同一任务建立新令牌并续做。
- 系统保存面板产生真实文件，正文、字节及原生 `documentUrl` 与指定路径一致。文件存在、窗口标题或保存快捷键返回均不足以判定成功。
- 模型自然结束，普通任务内不出现重复审批；没有由验收器代批、代写或以取消制造完成。
- 跨应用页面实际接收输入和所选文件字节，并由目标应用原生状态读到本轮成功标记。

## 回归与负例

| 范围 | 入口 |
| --- | --- |
| 前端消息停止、普通消息续接与确认状态 | `pnpm test` |
| Runtime journal、分页与任务证据 | `pnpm test:scripts` |
| AX/UIA、引用、焦点、取消和边界 | `pnpm test:desktop-native` |
| 主程序和 Runtime 类型检查 | `cargo check --locked --manifest-path src-tauri/Cargo.toml --lib` |
| 真实 ACP 启停与工具配置恢复 | `pnpm test:runtime-smoke` |

macOS 原生模块测试需要可访问图形会话，但普通测试不派发输入。可在已经安装对应 Rust 目标时用 `cargo check --locked --manifest-path scripts/desktop-native-check/Cargo.toml --target x86_64-pc-windows-msvc` 检查 Windows 类型；这不等于 Windows 实机通过。

负例应覆盖跨会话/过期引用、变化目标、歧义与截断、受保护/禁用控件、缺页或重复页、错误模型、历史回放、缺少真实新建、正文不符、未保存及终端替代。不能删除这些约束来获得通过。

## 记录与平台边界

保留原始失败、重试和最终核验，不把后续补丁当成正在运行的旧应用已经更新。报告应区分单次原生调用、模型参数错误、系统授权和提供方异常；某个应用查询失败不能直接推断全局权限丢失。

休眠、锁屏、人工等待和验收活动时限分别记录；期限只暂停、不自动恢复任务。清理时仅处理本次明确归属的 PID，记录正常退出或强制收尾的区别。完整证据留在私有验收目录或 CI artifacts，长期文档保留方法与限制。

Windows 在实际交互桌面另行验收原生输入、文件面板和暂停恢复；安装包与通知检查见 [Windows 桌面验收](../windows-desktop-feedback-acceptance.md)。自绘界面、受保护内容、无限长文读取和 provider 硬挂起的限制见 [原生控件说明](README.md#平台限制)。性能比较见 [性能验证](performance.md)。

## 本次改造新增覆盖

- 默认原生模块回归直接包含生产任务状态、后果策略、已安装目标目录、Office 内容核验、浏览器 loopback 配对、输入保护、跨会话占用和协议边界。
- `pnpm test:desktop-helper` 启动真实生产 helper 协议，验证宿主与 helper PID 不同及父进程身份认证，不需要系统辅助功能权限，不派发输入。
- `pnpm test:desktop-browser` 使用隔离 headless Chromium 执行生产 CDP 集成用例：真实点击与变化拒绝、跨标签页下载、文本/选择输入、iframe 父层遮挡、开放 Shadow DOM、frame 文件选择和同 URL 重载后旧引用/cursor 拒绝。该测试不经过模型，也不控制用户现有浏览器，不替代扩展实装验收。
- `scripts/test-browser-extension.mjs` 在假 Chrome API 中执行随包 service worker，检查 popup 来源、loopback 配对、授权标签页、CDP 白名单、连接中暂停、排队输入撤销、恢复和换代。
- `pnpm test:ui:computer-task` 渲染生产 ChatView、Composer 与执行过程，检查 1024×680 明暗主题及 1440×900 布局，覆盖现有停止按钮、普通消息续接、过程中的运行/未知/完成/停止状态，并断言不出现桌面专用控制或浮窗接口调用。该证据明确标为 `synthetic-production-chat`，不能代替 Tauri 窗口或真实系统输入验收。

真实扩展验收还需在受支持的 Chrome/Edge 加载打包目录，使用合成登录页和合成文件分别验证：只列出所选标签页、同任务原生/网页混用、可访问 frame/开放 Shadow DOM、页面同 URL 重载拒绝旧引用、真实条件核验、人工 debugger 断开、暂停确认后无后续输入和断开后不回退到其他登录环境。不得使用真实业务消息或付款完成自动化测试。

Windows 交叉编译只证明当前类型适配；标准文件面板、Unicode 输入、全局快捷键、人工输入打断、UAC/高权限拒绝和 helper 回收仍须 Windows 实机。macOS 的签名、TCC 和事件 tap 同样需要实际安装包及图形会话验证。没有新的实机证据时，不给出与 Codex 等同的成功率或后台输入承诺。

此前的受控 Chromium 集成（4 项）和 ACP 无模型冒烟（7 个隔离场景）结果保留为上一版记录。本次新增后台实机验收直接调用生产原生模块，不经过完整模型或宿主消息流程；消息准入、取消队列及任务状态分别由宿主测试覆盖。

本次修复包括：独立栏/浮窗入口及窗口权限残留、文字停止后无法终止原生执行、旧回复显示新任务状态、模型结束后残留授权、发送新要求时旧模型使用新授权、全局人工输入暂停、同目标冲突在模型思考空档丢失、定时抢回、后台启动意外激活，以及后台组合键不被 AppKit 菜单处理等问题。原生文本替换优先使用实际 UTF-16 选区；快捷键优先执行唯一、启用的实际菜单动作。pipe 驱动的 helper 主动处理有限 AppKit 通知，并使用同步系统前台身份，避免缓存状态误判。

实测发现 PID 定向的后台普通鼠标事件可能仅抵达应用事件监测器，没有命中目标控件。该不可靠路径已移除；macOS 只承诺 advertised AXPress 的后台单击，双击/无原生动作需显式前台观察和坐标路径。不能把事件派发当作实际点击成功。

本次没有让真实模型操作业务桌面应用，没有对用户现有浏览器安装/配对扩展，没有执行 Windows 实机或 macOS 签名安装包的 TCC/快捷键验收。人工输入冲突按 native 目标 PID 判断，验证包括生产协调器回归和实际 monitor 可用性；没有模拟真人的硬件输入，扩展浏览器仍依赖页面变化校验、debugger 断开和停止确认，尚未接入等价的原生 PID 输入锁；用户同时编辑受控标签页仍存在竞态。上述结果不构成与 Codex 相同任务成功率或任意软件后台输入能力的证明。

## 微信失败后的修复验收

原始日志显示：目标窗口已经打开，但只有窗口和三个窗口按钮，没有原生文本控件；截图和菜单快捷键误依赖 `AXFocusedUIElement`，导致视觉路径也被拒绝。原先的整轮前台冲突锁使后续尝试持续失败，截图又可能跟随其他前台应用。单次任务产生了 57 次工具调用而没有实际输入，缺少宿主收敛。不能仅凭其中一次权限错误归因于系统授权，也没有证据把争用归责于用户。

新增验收分为三个层次：

- `pnpm test:desktop-visual`：编译两份独立临时 macOS App。自绘 NSView 显式不提供 AX 输入焦点；生产原生模块执行无焦点菜单命令、绑定窗口捕获、点击、Unicode 输入、夹具发送和目标位置滚动。文件逐字核验；其他应用在前台时，捕获和旧帧输入必须拒绝。所有写入限于夹具。
- `actual_wechat_visual_preflight`：显式启用后仅重新打开/观察本机微信，核验没有 AX 输入焦点时仍可得到绑定微信窗口的原生输入帧。没有向微信派发点击、文字、回车或发送，不证明真实联系人投递已完成。
- `--opaque-flow`：生产内嵌 Tauri 应用、配置中的实际 MiniMax 模型、正常 Composer 和 ACP Runtime/MCP 的完整流程；先发送缺正文请求，再用普通“继续”验证不能绕过，最后补充本轮独有正文和夹具路径。在同一 taskId 完成真实 UI 操作，精确文件核验和 `automation_complete`；驱动只提交普通消息及读取证据，不代写目标内容。

真实模型资源必须使用显式的私有配置。驱动生成独立 home、应用副本、工作区、journal 和报告；报告只包含模型身份，不应包含凭据。验收后移除临时模型资源和配置中的凭据。默认忽略的测试必须单独运行并记录，不能把未运行当作通过。

## 应用定向执行实机夹具

`pnpm test:desktop-background` 仅在 macOS 显式运行：编译两份专用临时 App，一份留在前台并遮挡另一份，直接调用生产原生模块验证后台 AX 值设置、Unicode 键盘替换、窗口菜单快捷键、AXPress 和目标窗口捕获；没有原生按下动作的点击必须拒绝且无鼠标事件派发。断言前台 PID、系统指针与前台文本保持不变；截图须来自被遮挡目标窗口的独特背景色。所有输入与输出限于临时夹具，结束时终止自有 PID 并恢复原焦点，不使用业务应用。该测试不替代真实模型、完整宿主消息准入或其他应用兼容性验收。

## 真实微信发送验收（2026-11-13，通过）

用户明确授权向“文件传输助手”发送一次“EchoAgent 微信端到端测试，请忽略。”。最终在 macOS 15.8.3、微信 4.2.0 上，通过正常 Composer、实际 MiniMax-M3.1-Flash、生产 ACP Runtime/MCP 和原生界面完成发送；没有使用微信协议、数据库或脚本代发。

最终一次运行共 26 个唯一工具请求。测试正文输入一次，发送按钮点击一次。先核验文件传输助手标题，再检查草稿；发送后，宿主对会话标题、聊天记录中的正文区域和空输入框提示分别 OCR 核验，正文区域排除了输入框及联系人列表。`automation_complete` 首次错误引用旧凭证被拒绝，随后使用发送后的有效凭证完成。两次错误复用已消费帧的输入也均在派发前拒绝；验收后补充了单次帧参数说明和恢复提示，避免重新截图后重复已成功的点击。

模型流程结束后另行只读复核：正确会话中可见新发送的绿色气泡，正文一致；输入框为空，发送按钮禁用，未见新消息的发送失败标记。独立新截图的三个 OCR 条件再次全部通过。全过程只实际发送这一条测试正文，未操作其他联系人或修改微信设置。可公开的最小证据见 [验收记录](wechat-acceptance-2026-11-13.json)；完整画面和原始日志仅留在本机私有验收目录。
